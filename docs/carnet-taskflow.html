Repères du projet

TaskFlow est une API de gestion de projets et de tâches. Le code de travail est dans le dépôt GitHub public de l’apprenant.

À retenir : le navigateur fait une requête HTTP ; Node exécute le serveur ; Express associe une requête à une route ; TypeScript vérifie les types avant l’exécution.
Node.js24.18.0 sur la machine de l’apprenant ; ligne 24 LTS, support jusqu’en avril 2028.
pnpm12.6.0, version épinglée dans le projet.
TypeScript7.0.2, compilateur natif Go, installé en dépendance de développement.
Express5.2.1 avec les types Express 5.0.6.
Prisma7.10.0 — épinglé, car le tag latest pointe aujourd’hui sur une candidate 8.0.
SQLitevia @prisma/adapter-better-sqlite3 7.10.0 ; fichier local dev.db.

Les versions et conventions doivent être revérifiées avant d’ajouter un nouvel outil ou une nouvelle commande.

01

Semaine 1 · fondations TypeScript

Un type décrit les formes autorisées ; il ne crée pas à lui seul de données à l’exécution.

1. Alias d’objet : décrire un utilisateur

validé

Pourquoi : TypeScript peut vérifier qu’un objet contient les propriétés attendues. type User décrit la forme ; currentUser contient une valeur réelle.

type User = {
  id: string;
  name: string;
  email: string;
};

const currentUser: User = {
  id: "user-001",
  name: "Elfred",
  email: "elfred434@gmail.com",
};
Ponctuation : dans la définition du type, les propriétés sont séparées par des points-virgules ; dans l’objet de valeurs, elles sont séparées par des virgules. Les textes ont des guillemets.
Question de rappel

Si email vaut le nombre 42, le contrôle TypeScript doit signaler une incompatibilité : email attend un string.

2. Interface : décrire un projet

validé

Pourquoi : une interface décrit elle aussi une forme d’objet. Ici, Project est le contrat des données d’un projet ; currentProject est l’objet qui le respecte.

interface Project {
  id: string;
  name: string;
  ownerId: string;
}

const currentProject: Project = {
  id: "proj-001",
  name: "Apprendre Tanstack",
  ownerId: "user-001",
};
À retenir

Pour ces formes d’objet simples, un alias type et une interface peuvent tous deux convenir. Il n’y a pas une règle absolue qui rendrait l’un toujours supérieur à l’autre.

3. Union : limiter les statuts

validé

Pourquoi : un string libre autoriserait les fautes de frappe. Une union de chaînes littérales limite la valeur à des choix connus ; | signifie « ou ».

type TaskStatus = "todo" | "in-progress" | "done";

type Task = {
  id: string;
  title: string;
  projectId: string;
  status: TaskStatus;
};

Une valeur "finished" n’est pas membre de cette union, donc le contrôle TypeScript la refuse dans le code typé.

Limite importante : le type ne valide pas automatiquement un JSON reçu sur HTTP. Les données externes devront être contrôlées à l’exécution avec Zod plus tard.

4. Générique : réutiliser une enveloppe

validé

Pourquoi : le paramètre T est un emplacement réservé à un type. Le type choisi au moment de l’utilisation précise ce que contient data.

type ApiResponse<T> = {
  data: T;
};

// T devient Task
const oneTask: ApiResponse<Task> = {
  data: currentTask,
};

// T devient un tableau de Task
const manyTasks: ApiResponse<Task[]> = {
  data: tasks,
};
Question de rappel

Dans ApiResponse<Project>, T est remplacé par Project ; data doit donc avoir la forme d’un projet.

5. Tableau : représenter une liste

validé

Pourquoi : l’API doit pouvoir représenter plusieurs tâches. Task[] désigne un tableau dont chaque élément doit respecter Task.

export const tasks: Task[] = [currentTask];

export const tasksResponse: ApiResponse<Task[]> = {
  data: tasks,
};

Le tableau contient une tâche pour l’instant ; on pourra en ajouter d’autres quand on construira les opérations d’écriture.

6. Vérifier n’est pas exécuter

validé

pnpm exec tsc --noEmit vérifie le projet sans générer de JavaScript. pnpm exec tsc compile selon tsconfig.json ; node dist/server.js exécute ensuite le JavaScript généré.

pnpm exec tsc --noEmit  # contrôle seulement
pnpm exec tsc           # génère dist/
node dist/server.js     # lance le serveur

8. Une route associe méthode et chemin

validé

Une route Express choisit un gestionnaire selon la méthode HTTP et le chemin. Dans http://localhost:3000/tasks/current, le chemin est /tasks/current ; le navigateur utilise GET.

app.get("/tasks/current", (_request, response) => {
  response.json(currentTaskResponse);
});

app.get("/tasks", (_request, response) => {
  response.json(tasksResponse);
});

app.get("/projects/current", (_request, response) => {
  response.json(currentProjectResponse);
});

La même enveloppe générique ApiResponse<T> peut contenir une tâche ou un projet. currentProjectResponse est exporté depuis domain.ts, puis importé par le serveur.

Middleware · journaliser les requêtes

Le middleware de journalisation s’exécute avant les routes ; le terminal a déjà affiché GET /tasks.

Une étape avant la route

testé localement

Un middleware peut inspecter une requête et laisser Express continuer. Il est placé avant les routes ; next() transmet le contrôle à la prochaine étape au lieu de terminer la réponse.

app.use((request, _response, next) => {
  console.log(request.method, request.path);
  next();
});

Guide Express sur les middlewares · API Express : req.method et req.path

Question de rappel

Que se passerait-il si ce middleware n’envoyait aucune réponse et n’appelait jamais next() ? La requête resterait en attente.

04

Corps JSON d’une requête

Préparer Express à lire les données JSON envoyées à TaskFlow.

Transformer le JSON reçu en objet JavaScript

validé avec POST

Pourquoi : pour créer une tâche, le client devra envoyer ses informations au serveur. Ces données voyagent dans le corps de la requête HTTP. Le middleware intégré express.json() lit les requêtes déclarées comme JSON et place le résultat analysé dans request.body.

Le trajet : texte JSON envoyé par le client → express.json() → objet JavaScript disponible dans request.body → route Express.
// Après const app = express(), avant les routes
app.use(express.json());
Deux actions différentes : express.json() fabrique la fonction middleware ; à elle seule, elle ne l’ajoute pas à l’application. app.use(...) l’enregistre pour qu’Express l’exécute. Dans app.use(express.json()), l’appel intérieur se fait d’abord, puis sa fonction résultat est donnée à app.use. Écrire seulement express.json(); crée la fonction puis l’ignore. C’est une syntaxe valide, donc TypeScript ne peut pas deviner l’intention manquante.

Place app.use(express.json()) après la création de app et avant les routes qui lisent request.body. Le middleware ne vérifie pas que les champs reçus sont corrects : les données envoyées par un client restent à valider.

Documentation officielle Express 5 : express.json()

Question de rappel : que fait chaque partie ?

express.json() crée le middleware ; app.use(...) l’enregistre. Ensemble, ils font analyser le corps JSON et rendent le résultat accessible sur request.body. Cela ne garantit pas que title est présent ou que status est autorisé : cette validation viendra plus tard.

05

POST /tasks · demander la création d’une tâche

On distingue lire la liste et demander l’ajout d’une tâche.

La méthode HTTP et le chemin choisissent la route

testé

Pourquoi : GET /tasks sert à lire la liste existante. Pour demander au serveur de créer une tâche, TaskFlow utilisera POST /tasks et les données du corps JSON. Le chemin reste /tasks, mais la méthode change ; Express distingue les deux routes par cette paire méthode + chemin.

À comparer :
GET /tasks → lire la liste
POST /tasks → demander la création d’une tâche à partir des données envoyées

Important : le mot POST ne sauvegarde rien à lui seul. Il sélectionne un gestionnaire. C’est le code de ce gestionnaire qui devra lire request.body et ajouter la tâche au tableau en mémoire.

Dans le gestionnaire, trois actions

  1. Importer le tableau tasks depuis domain.ts : c’est la liste gardée en mémoire.
  2. Appeler tasks.push(request.body) : push ajoute l’objet reçu à la fin du tableau. request.body vient du middleware JSON.
  3. Renvoyer tasksResponse avec response.json(...) ; son enveloppe data contient ce même tableau mis à jour.
app.post("/tasks", (request, response) => {
  tasks.push(request.body);
  response.json(tasksResponse);
});
Garder la même forme de réponse : tasks est le tableau brut ; tasksResponse est l’objet enveloppe { data: tasks }. Utiliser response.json(tasksResponse) dans POST conserve la même forme que GET. Dans le gestionnaire Express, request est déjà fourni comme paramètre : aucun import { request } from "http" n’est nécessaire.
Limite de cette première version : request.body vient d’un client et n’est pas validé automatiquement par TypeScript. Pour l’exercice, envoie un objet qui respecte bien la forme Task. Plus tard, Zod vérifiera les données reçues. Le tableau est en mémoire : le redémarrage du serveur le réinitialise.

Pour notre premier test, le corps sera un objet de forme Task avec id, title, projectId et status. Nous fournirons l’id manuellement pour l’exercice ; sa création automatique viendra plus tard.

Pour tester la route, PowerShell doit envoyer un corps JSON. Si un accent ressort sous la forme � jusque dans la réponse vue au navigateur, il a été remplacé avant d’être stocké : ce n’est pas seulement l’affichage du terminal. Selon la version de PowerShell, envoyer directement une chaîne peut mal encoder les caractères Unicode. On peut convertir explicitement le texte en octets UTF-8 et déclarer cet encodage :

$taskJson = '{"id":"task-003","title":"Créer via POST","projectId":"proj-001","status":"todo"}'
$utf8Body = [System.Text.Encoding]::UTF8.GetBytes($taskJson)
Invoke-RestMethod -Uri "http://localhost:3000/tasks" `
  -Method Post `
  -ContentType "application/json; charset=utf-8" `
  -Body $utf8Body

GetBytes transforme la chaîne en octets UTF-8 ; charset=utf-8 indique à Express comment les décoder. Si l’accent est déjà remplacé quand tu affiches $taskJson avant l’envoi, le problème se situe plus tôt.

Documentation Microsoft : Invoke-RestMethod · Exemple du problème Unicode dans Invoke-RestMethod

Question de rappel : pourquoi GET et POST peuvent-ils partager /tasks ?

Parce que la méthode HTTP fait partie de l’identification de la route, avec le chemin.

Question de rappel : que fait tasks.push(request.body) ?

push ajoute l’objet reçu à la fin du tableau en mémoire. Cela ne valide pas l’objet et ne l’écrit pas sur le disque.

Un paramètre d’URL pour viser une tâche

Passer l’identifiant d’une tâche dans le chemin de la requête.

Le placeholder :id

notion en cours

Pourquoi : GET /tasks vise toute la liste. Pour viser une tâche particulière dans TaskFlow, le chemin peut contenir son identifiant. Le symbole : indique à Express qu’un morceau du chemin doit être capturé comme paramètre.

Exemple TaskFlow :
Modèle de route : /tasks/:id
Requête reçue : /tasks/task-003
Valeur capturée : request.params.id vaut la chaîne "task-003"

:id est le nom donné au paramètre dans le modèle de route. request.params.id est la valeur réelle capturée dans l’URL ; ici, c’est un texte, car les identifiants Task sont des chaînes.

07

Retrouver une tâche dans le tableau

Utiliser l’identifiant capturé dans l’URL pour repérer l’objet correspondant.

La méthode find()

testé

Pourquoi : request.params.id donne l’identifiant demandé, mais ce texte n’est pas la tâche elle-même. tasks.find(...) parcourt le tableau et cherche le premier élément qui satisfait une comparaison.

const foundTask = tasks.find(
  (oneTask) => oneTask.id === request.params.id
);
  • oneTask représente l’élément examiné à chaque tour.
  • === vérifie si son identifiant est exactement égal à celui capturé dans l’URL.
  • find() renvoie l’objet trouvé, ou undefined si aucun élément ne correspond.
Application TaskFlow : avec GET /tasks/task-002, la route reçoit request.params.id === "task-002", puis recherche la tâche dont id vaut "task-002".
Test observé : GET /tasks/task-001 et GET /tasks/task-002 ont chacun renvoyé l’objet correspondant sous data.

La route GET /tasks/:id est placée après la route statique GET /tasks/current : ainsi, :id ne capture pas le mot current. La réponse « identifiant absent » sera traitée dans l’étape suivante ; ici, on teste d’abord un identifiant qui existe.

Question de rappel

Si la liste contient une tâche avec id: "task-002", quel objet find() renvoie-t-il quand l’URL est /tasks/task-002 ?

08

Répondre si l’identifiant est introuvable

Une recherche peut réussir ou ne trouver aucun objet.

Le résultat absent et le statut 404

testé

Pourquoi : find() renvoie undefined si aucun identifiant ne correspond. L’API ne doit pas faire croire qu’une tâche existe : elle doit répondre 404 Not Found, c’est-à-dire « ressource introuvable ».

app.get("/tasks/:id", (request, response) => {
  const foundTask = tasks.find(
    (oneTask) => oneTask.id === request.params.id
  );

  if (!foundTask) {
    response.status(404).json({ error: "Tâche introuvable" });
    return;
  }

  response.json({ data: foundTask });
});
  • if (!foundTask) vérifie qu’aucune tâche n’a été trouvée. Ici, !undefined vaut true.
  • response.status(404) choisit le code HTTP ; .json(...) envoie aussi un message JSON.
  • return arrête le gestionnaire après la réponse d’erreur ; sinon le code pourrait continuer et tenter d’envoyer une deuxième réponse.
Pourquoi return est indispensable : le bloc if ne met pas fin à toute la fonction. Sans return, après avoir envoyé le JSON 404, JavaScript sort seulement des accolades du if puis continue à la ligne suivante, qui essaie d’envoyer aussi la réponse normale. Node refuse cette deuxième réponse et affiche ERR_HTTP_HEADERS_SENT. Le return fait quitter immédiatement le gestionnaire après le 404.
Résultat attendu : GET /tasks/id-inexistant reçoit le statut 404 et le JSON {"error":"Tâche introuvable"}. Pour une tâche existante, la réponse reste {"data":{...}}.
Question de rappel

Pourquoi met-on return après l’envoi de la réponse 404 ? Pour sortir du gestionnaire et ne pas tenter ensuite d’envoyer aussi la réponse normale.

Documentation officielle Express 5 : res.status()

09

Modifier une tâche avec PATCH

Changer un champ d’une tâche ciblée par son identifiant.

Une mise à jour partielle

testé

Pourquoi : si on veut seulement changer le statut d’une tâche, il n’est pas nécessaire de renvoyer toutes ses propriétés. PATCH /tasks/:id désigne la tâche avec son identifiant dans l’URL ; le corps JSON fournit le nouveau statut.

app.patch("/tasks/:id", (request, response) => {
  const foundTask = tasks.find(
    (oneTask) => oneTask.id === request.params.id
  );

  if (!foundTask) {
    response.status(404).json({ error: "Tâche introuvable" });
    return;
  }

  foundTask.status = request.body.status;
  response.json({ data: foundTask });
});
  • app.patch associe la méthode PATCH à la route ; l’identifiant vient de request.params.id.
  • foundTask.status = ... remplace seulement la valeur du statut ; les autres propriétés de cette tâche restent les mêmes.
  • Le statut reçu doit être une valeur prévue par TaskStatus, par exemple "done". request.body reste une entrée externe non vérifiée ; Zod s’en chargera dans une étape ultérieure.

Pour tester, le corps JSON ne contient que le champ à modifier : {"status":"done"}. Après le PATCH, GET /tasks/task-002 doit montrer le statut "done".

Test observé : PATCH /tasks/task-002 a renvoyé la tâche avec le statut "done".
$patchJson = '{"status":"done"}'
Invoke-RestMethod -Uri "http://localhost:3000/tasks/task-002" -Method Patch -ContentType "application/json" -Body $patchJson

Le changement reste en mémoire : redémarrer le serveur rétablit les tâches initiales. Si PowerShell refuse la méthode Patch, vérifier sa version avec $PSVersionTable.PSVersion.

Question de rappel

Pourquoi le corps de cet exemple contient-il seulement status au lieu de l’objet Task complet ? Parce que cette opération ne modifie qu’un seul champ.

10

Supprimer une tâche avec DELETE

Retirer de la liste la tâche désignée par son identifiant.

Trouver la position, puis retirer l’élément

testé

Pourquoi : DELETE /tasks/task-002 indique au serveur quelle tâche supprimer. Pour la retirer du tableau, il faut d’abord trouver sa position.

app.delete("/tasks/:id", (request, response) => {
  const taskIndex = tasks.findIndex(
    (oneTask) => oneTask.id === request.params.id
  );

  if (taskIndex === -1) {
    response.status(404).json({ error: "Tâche introuvable" });
    return;
  }

  tasks.splice(taskIndex, 1);
  response.json(tasksResponse);
});
  • findIndex(...) renvoie la position de l’élément trouvé : par exemple 0 pour le premier ; il renvoie -1 s’il n’y a aucune correspondance.
  • On vérifie -1 avant suppression. Sinon, splice(-1, 1) retirerait par erreur le dernier élément.
  • splice(taskIndex, 1) signifie : à partir de cette position, retirer un élément. La méthode modifie le tableau existant.
  • La réponse renvoie tasksResponse, qui contient ce même tableau désormais mis à jour.

Le DELETE n’a pas besoin de corps JSON dans cet exercice : l’URL fournit l’identifiant. Après suppression de task-002, GET /tasks doit afficher la liste sans cette tâche.

Invoke-RestMethod -Uri "http://localhost:3000/tasks/task-002" -Method Delete
Test observé : la réponse du DELETE ne contient plus task-002 ; la tentative de relire l’identifiant supprimé renvoie 404 Tâche introuvable.
Question de rappel

Pourquoi teste-t-on taskIndex === -1 avant d’appeler splice ?

11

Du tableau en mémoire à une base SQLite

Pourquoi TaskFlow va bientôt stocker ses tâches dans un fichier de base de données.

Des données qui survivent au redémarrage

choix retenu pour la suite

Pourquoi : le tableau tasks vit dans la mémoire du processus Node.js. Quand le serveur s’arrête, cette mémoire disparaît et le tableau est recréé au prochain démarrage. Une base SQLite écrit les données dans un fichier local, par exemple dev.db, qui reste sur le disque.

Choix pédagogique : commencer avec SQLite, une vraie base relationnelle sous forme de fichier, évite d’installer et d’administrer un serveur de base de données. Comme TaskFlow est collaboratif, PostgreSQL pourra être évalué pour un déploiement plus ambitieux.
Choix de version : pour suivre le programme prévu — schema.prisma, Prisma Client typé et migrations — on utilisera délibérément le parcours Prisma ORM 7. Les docs Prisma présentent aussi le parcours Prisma 8, qui introduit une approche de contrats et un flux de migrations différent ; on pourra l’étudier plus tard, sans mélanger les deux.

Prisma n’est pas la base de données

SQLite conserve réellement les données dans son fichier. Prisma est l’intermédiaire utilisé par le code TypeScript pour décrire les modèles, produire un client typé et envoyer des opérations à la base.

Le trajet des données :
serveur TaskFlow en TypeScript → Prisma Client typé → fichier SQLite dev.db
Le schéma Prisma décrit la forme voulue ; les migrations créent ou modifient les tables SQLite.
Question de rappel

Après un redémarrage de Node.js, quelle donnée reste disponible : l’ajout dans le tableau tasks, ou une tâche déjà écrite dans le fichier SQLite ?

Qui garde les données : Prisma ou SQLite ?

SQLite conserve physiquement les données dans dev.db ; Prisma fournit au code TypeScript une manière typée de décrire le modèle et d’interroger cette base.

Les paquets Prisma n’ont pas le même rôle

  • prisma : commande de développement pour initialiser le schéma et les migrations.
  • @prisma/client : bibliothèque utilisée par le serveur TaskFlow pendant son fonctionnement.
  • @prisma/adapter-better-sqlite3 : relie Prisma Client au fichier SQLite.
  • @types/better-sqlite3 et dotenv : types TypeScript du pilote et lecture de la configuration locale.
pnpm add -D prisma@7 @types/better-sqlite3
pnpm add @prisma/client@7 @prisma/adapter-better-sqlite3 dotenv

-D place les outils de développement dans devDependencies ; les autres paquets sont nécessaires à l’application à l’exécution. TaskFlow possède déjà @types/node, donc inutile de le réinstaller.

Pourquoi pnpm a bloqué les scripts ?

Depuis pnpm 10, les scripts d’installation des dépendances peuvent être bloqués jusqu’à approbation explicite. Cette protection a interrompu la première tentative ; les scripts attendus étaient ceux de @prisma/engines et prisma (outils Prisma), ainsi que better-sqlite3 (pilote SQLite natif).

Avec pnpm 12, pnpm approve-builds enregistre les choix dans pnpm-workspace.yaml, afin que le projet garde une règle explicite sur les scripts autorisés. On approuve seulement les dépendances attendues, jamais tout en bloc. Dans TaskFlow, les trois scripts nécessaires sont maintenant autorisés et ont été exécutés avec succès.

Installation vérifiée : le dépôt contient Prisma CLI, Prisma Client et l’adaptateur SQLite en version 7.10.0, ainsi que dotenv 18.0.4. La commande pnpm list --depth 0 a confirmé leur installation.

Initialiser Prisma 7 sans encore créer de table

Préparer le schéma, la configuration et le chemin du client généré avant de modéliser TaskFlow.

Le squelette du projet

à pratiquer

Pourquoi : Prisma a besoin d’un fichier de schéma pour décrire les futures tables et d’une configuration pour savoir où se trouve la base. On prépare ces fichiers avant d’écrire le modèle Task.

pnpm exec prisma init --datasource-provider sqlite --output ../src/generated/prisma
  • pnpm exec lance l’outil Prisma installé dans ce projet, sans installation globale.
  • prisma init crée les fichiers de départ ; il ne crée pas encore de table.
  • --datasource-provider sqlite choisit SQLite comme base.
  • --output ../src/generated/prisma place plus tard le client TypeScript généré sous src. Ce chemin est relatif au schéma ; cela respecte le rootDir: "./src" actuel de TypeScript.

Avec Prisma 7.10, la commande crée notamment prisma/schema.prisma, prisma7.config.ts et .env. Le schéma est un plan : la vraie table SQLite ne sera créée qu’avec une migration, dans une étape ultérieure.

13

Semaine 3 · le schéma : décrire les tables

Un seul fichier décrit la forme des données. Prisma en tire le SQL, les types et les requêtes.

Pourquoi un schéma plutôt que des types écrits à la main

validé

Pourquoi : en semaine 1, la forme des données vivait dans src/domain.ts et le stockage dans un tableau tasks à côté. Deux sources de vérité pour la même information : ajouter un champ obligeait à penser aux deux, et rien ne valait les données à l’exécution.

Le schéma est la source unique. À partir de prisma/schema.prisma, Prisma génère le SQL des tables (migrations), les types TypeScript de ces tables, et des fonctions de requête typées. On écrit la forme une fois.

Concrètement, src/domain.ts est maintenant doublé : Task, Project et User existent en version générée, dans src/generated/prisma/.

Un modèle = une table

validé
model User {
  id           String   @id @default(uuid())
  name         String
  email        String   @unique
  passwordHash String
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
Règle de traduction : le nom du champ d’abord, le type ensuite — title String, jamais String title. Un champ par ligne, et pas de virgule en fin de ligne (contrairement à un objet JavaScript).
  • @id — clef primaire : identifiant unique de la ligne.
  • @default(uuid()) — Prisma génère un UUID si le client n’en fournit pas. 122 bits d’aléa, donc non devinables. Avec des ids séquentiels (1, 2, 3), un attaquant énumère /tasks/1, /tasks/2… et lit les ressources des autres. La faille s’appelle IDOR (Insecure Direct Object Reference).
  • @unique — la base refuse les doublons, pas seulement le code applicatif.
  • @default(now()) — date de création, posée par le serveur de base.
  • @updatedAt — Prisma met à jour ce champ tout seul à chaque écriture.
Question de rappel

Pourquoi @unique sur email est-il plus fort qu’une vérification faite dans le code TypeScript avant d’enregistrer ?

L'enum : limiter les valeurs, mais jusqu'où ?

nuance importante

Pourquoi : en semaine 1, type TaskStatus = "todo" | "in-progress" | "done" interdisait les fautes de frappe à la compilation. L’enum Prisma est l’équivalent pour la base.

enum TaskStatus {
  todo
  in_progress
  done
}

model Task {
  id        String     @id @default(uuid())
  title     String
  projectId String
  status    TaskStatus @default(todo)
}
Le tiret est interdit. La union d’origine était "in-progress". Un enum Prisma est un identifiant : le tiret n’y est pas autorisé, d’où in_progress. C’est la seule adaptation nécessaire.
L'enum ne protège PAS la base. Le SQL généré est "status" TEXT NOT NULL DEFAULT 'todo' — du texte brut, sans contrainte CHECK. SQLite ne connaît pas les enums. Testé : en forçant une valeur invalide, c’est Prisma Client qui refuse (Invalid prisma.task.create() invocation), pas la base. Un script SQL brut ou un autre outil pourrait écrire "finished" sans erreur.

Conséquence directe pour la suite : la validation des données qui entrent par HTTP devra se faire à la frontière, avec Zod, en semaine 4. Se fier au type ne suffit pas.

Question de rappel

Qui refuse une valeur d’enum invalide : la base SQLite, Prisma Client, ou TypeScript ? Les trois, deux, un seul ?

Le ? ne veut pas dire « optionnel »

piège de traduction

Pourquoi : en TypeScript, prop?: string signifie que la propriété peut être absente de l’objet. En Prisma, String? signifie autre chose.

// Schéma Prisma
passwordHash String?

// Type généré
passwwordHash: string | null   // propriété TOUJOURS présente, valeur nullable

// Ce n'est PAS ça :
passwwordHash?: string         // propriété qui peut manquer
Côté base : sans ?, la colonne est NOT NULL et la base refuse d’enregistrer une ligne sans valeur. Avec ?, la colonne est nullable et la base accepte. Le test à écrire est donc if (user.passwordHash === null), jamais if (!("passwordHash" in user)).
Pourquoi passwordHash est obligatoire : un utilisateur sans mot de passe est un compte ouvert. Et ajouter plus tard une colonne NOT NULL à une table déjà peuplée est refusé par SQLite faute de valeur par défaut — mieux vaut la déclarer dès le début.

Ce que Prisma génère à partir de 3 lignes

validé
// src/generated/prisma/enums.ts — généré, ne pas modifier
export const TaskStatus = {
  todo: 'todo',
  in_progress: 'in_progress',
  done: 'done'
} as const

export type TaskStatus = (typeof TaskStatus)[keyof typeof TaskStatus]

Un objet runtime (TaskStatus.todo vaut 'todo', utilisable dans le code) et un type dérivé de cet objet. Une source, deux vues — le même motif que ApiResponse<T>, sauf que la source est le schéma.

Remarque : Prisma n’a pas généré un enum TypeScript, mais un const objet. C’est la forme moderne, compatible avec l’exécution directe par Node (erasableSyntaxOnly interdit les enum).

La commande de génération

pnpm exec prisma generate

À relancer à chaque modification du schéma. Le dossier src/generated/prisma/ est dans .gitignore : il n’est pas versionné, il est recréé. Pour ne jamais l’oublier après une installation, un script postinstall dans package.json l’automatise.

Question de rappel

Tu modifies schema.prisma puis tu écris du code qui utilise le nouveau champ. Le compilateur dit « propriété inexistante ». Quelle commande as-tu oubliée ?

Le client et l'adapter

Un schéma ne sait pas parler à une base. Il faut une connexion et une interface typée.

Pourquoi un adapter est obligatoire en Prisma 7

validé

Pourquoi : en Prisma 6 et avant, un moteur écrit en Rust faisait le lien entre le client et la base. En Prisma 7, ce moteur a été supprimé et remplacé par du TypeScript compilé en WebAssembly. Conséquence mécanique : tu dois fournir toi-même le pilote.

Le trajet :
ton code → PrismaClient (interface typée) → PrismaBetterSqlite3 (l’adapter) → better-sqlite3 (le pilote) → fichier dev.db
Sans l’adapter, new PrismaClient() ne sait pas où écrire.

Un seul client, partagé

validé
// src/db.ts
import { PrismaClient } from "./generated/prisma/client.js";
import { PrismaBetterSqlite3 } from "@prisma/adapter-better-sqlite3";
import path from "node:path";
import { fileURLToPath } from "node:url";

const currentDir = path.dirname(fileURLToPath(import.meta.url));
const databaseUrl = `file:${path.join(currentDir, "..", "dev.db")}`;

const adapter = new PrismaBetterSqlite3({ url: databaseUrl });

export const prisma = new PrismaClient({ adapter });
Pourquoi un fichier séparé : PrismaClient ouvre un pool de connexions. En créer un par requête épuiserait la base. Un module partagé = une seule instance, créée au démarrage. C’est le motif singleton.
Pourquoi .js et pas .ts dans l’import : on compile avec tsc (option A). À l’exécution, Node charge dist/db.js, et l’import doit pointer vers un fichier qui existe à ce moment-là. En option B (Node exécute le .ts directement), il faudrait écrire ./db.ts — Node résout les imports littéralement et ne trouverait pas de db.js.

Le piège du chemin relatif

vérifié par test

Pourquoi : DATABASE_URL="file:./dev.db" contient un chemin relatif. Or better-sqlite3 le résout par rapport au dossier courant (le CWD), pas par rapport au projet.

Test effectué : le même serveur, lancé depuis deux dossiers différents.
Depuis la racine du projet → {"data":[]} — la base migrée est trouvée.
Depuis /tmp → « The table main.Task does not exist » — un second fichier dev.db vide avait été créé dans /tmp.

Le correctif est import.meta.url, qui donne l’emplacement réel du module en cours, indépendamment du dossier de lancement. C’est la seule façon fiable en ESM de savoir « où je suis ».

Reste à savoir : le CLI Prisma, lui, lit DATABASE_URL depuis .env et résout ce chemin par rapport au CWD. Les deux composants ne résolvent donc pas le même chemin par le même mécanisme. Aujourd’hui le CLI échoue bruyamment s’il est lancé depuis le mauvais dossier (PrismaConfigEnvError), ce qui protège. Mais deux résolutions différentes finissent toujours par diverger un jour.
Question de rappel

Tu lances node dist/server.js depuis un sous-dossier du projet. Que risque-t-il de se passer, et quelle ligne de db.ts l’empêche ?

La première requête typée

validé
app.get("/tasks", async (_request, response) => {
  const tasks = await prisma.task.findMany();
  response.json({ data: tasks });
});
Pourquoi async / await : une requête base de données est une opération asynchrone. Sans await, on récupère une Promise et non les données — et response.json sérialiserait un objet Promise vide.
Pourquoi {"data":[]} et pas une erreur : le tableau est vide parce que la base est vide. L’API dit enfin la vérité : les deux tâches affichées en semaine 2 étaient codées en dur dans le fichier source. Une API qui renvoie des données inventées est plus dangereuse qu’une API qui renvoie une liste vide.

Les migrations

Le schéma est une intention. La base est la réalité. La migration est le pont.

L'erreur « The table does not exist »

erreur de départ

Pourquoi : le schéma déclare une table Task. La base dev.db était un fichier vide. Prisma Client croit le schéma, envoie SELECT … FROM Task, et la base répond qu’elle ne connaît pas cette table.

Message réel obtenu :
PrismaClientKnownRequestError: Invalid prisma.task.findMany() invocation: The table main.Task does not exist in the current database.

C’est l’erreur la plus courante chez les débutants Prisma, et elle a une cause unique : on a écrit le schéma, on a oublié de l’appliquer.

La commande

validé
pnpm exec prisma migrate dev --name init
  • migrate dev — compare le schéma à la base, génère le SQL manquant, l’applique.
  • --name init — nomme la migration ; le nom devient un dossier horodaté.

Elle produit notamment prisma/migrations/20260929203922_init/migration.sql, puis relance prisma generate automatiquement.

Le nom décrit le changement, pas le projet. Ajouter une colonne description donne --name add_task_description. Réutiliser init produirait deux dossiers nommés init, et personne ne saurait plus lequel fait quoi.

migrate dev ou db push ?

à ne pas confondre
migrate devCrée un fichier de migration, versionné, avec un historique ordonné. Demande confirmation en cas de perte de données.
db pushAucun fichier, aucun historique. Écrase la base pour la faire coller au schéma, parfois silencieusement.
Toujours migrate dev. db push est un raccourci pour un prototype ou une base jetable. Dans un projet, il fait diverger les bases de chaque machine sans laisser de trace.

Pourquoi versionner les migrations et pas dev.db

validé

Pourquoi : les deux viennent de la même commande, mais ils n’ont pas la même nature.

Les migrations, c’est la recette. Du SQL texte, portable, lisible, qui fonctionne sur n’importe quelle machine. C’est du code.
dev.db, c’est le gâteau. Un fichier binaire contenant l’état de la base locale, avec les données de test de chacun. C’est un artefact local.

On versionne la recette pour que n’importe qui puisse reconstruire le même gâteau. On ne versionne pas le gâteau : il écraserait celui des autres à chaque pull, et il ne contient aucune information que la recette ne puisse reproduire.

Erreur réellement commise : dev.db a été commité une fois. Il a fallu le retirer du suivi (git rm --cached dev.db) et ajouter *.db au .gitignore.

Autre différence décisive : les migrations sont ordonnées et historiques. Cette chronologie est l’information. Un fichier .db est un instantané sans mémoire.

Que deviennent les données existantes ?

validé

Pourquoi : c’est la question à se poser avant chaque migration sur une base qui contient déjà des lignes.

Réponse : migrate dev conserve les données. Ajouter description String? à Task attribue NULL aux lignes déjà présentes, parce que la colonne est nullable.
Le contraste qui compte : avec description String (sans ?), SQLite refuserait d’ajouter la colonne à une table peuplée, faute de valeur par défaut. C’est exactement le raisonnement qui avait fait déclarer passwordHash dès le début plutôt qu’en semaine 4.
Question de rappel

Tu ajoutes priority Int sans ? et sans @default à une table qui contient 500 tâches. Que fait la migration ?

Pièges rencontrés en route

Quatre erreurs réelles, toutes passées sans erreur de compilation. Le point commun : « ça compile » ne veut pas dire « c'est juste ».

1. La faute de frappe dans le schéma

silencieuse

Ce qui s’est passé : passwwordHash — trois p. Prisma a accepté, et a généré une colonne et un type portant le même nom.

// SQL généré
"passwwordHash" TEXT,

// Type généré
passwwordHash: string | null
Aucune erreur, aucun avertissement. TypeScript vérifie la cohérence, pas l’orthographe. Le bug serait apparu en semaine 4, quand user.passwordHash aurait été déclaré « propriété inexistante » — sans expliquer pourquoi.

Leçon : dans un schéma, une faute de frappe n’est pas une erreur de compilation, c’est une colonne mal nommée.

2. Deux clés « scripts » dans package.json

silencieuse

Ce qui s’est passé : un second bloc "scripts" a été ajouté au lieu de compléter le premier.

// Mesuré avec Node
require('./package.json').scripts
// → { postinstall: 'prisma generate' }     « test » a DISPARU
Le JSON autorise les clés dupliquées, et la dernière gagne. Le fichier reste valide, aucune erreur. Mais pnpm run ne listait plus aucun script utilisateur, et pnpm test aurait échoué avec ERR_PNPM_NO_SCRIPT.

Leçon : même famille de piège que la faute de frappe. Le fichier est syntaxiquement correct, donc aucun outil ne le signale.

3. app.listen commenté

bloquant

Ce qui s’est passé : en migrant les routes vers Prisma, la ligne app.listen(3000, …) a été mise en commentaire avec le reste de l’ancien code.

Symptôme : node dist/server.js → exit 0, aucune sortie, aucun port ouvert. Express monte l’application en mémoire puis le processus sort. Le curl échoue sans message utile.

Leçon : app.listen est l’interrupteur. Sans lui, tout le reste du code est inerte.

4. Le garde-fou devenu code mort

à surveiller

Ce qui s’est passé : en corrigeant le chemin relatif, la variable est devenue un template literal calculé. La vérification if (!databaseUrl) restée en place ne peut plus jamais être vraie.

const databaseUrl = `file:${path.join(currentDir, "..", "dev.db")}`;
if (!databaseUrl) { throw new Error("…") }   // !databaseUrl vaut toujours false
Un garde-fou qui ne peut pas se déclencher donne une fausse impression de sécurité. Il protège d’un risque qui n’existe plus.

Leçon : quand on déplace une vérification, il faut se demander si la condition qu’elle teste existe encore.

5. Tester sous Windows : le piège de curl

pratique

Ce qui s’est passé : une commande curl copiée depuis ce carnet a échoué sous PowerShell, avec deux erreurs qui n’avaient rien à voir avec le code de l’API.

curl: (6) Could not resolve host: application
TypeError: Cannot read properties of undefined (reading 'title')
Deux causes, toutes les deux propres à Windows :
1. La continuation de ligne. Dans bash c’est l’antislash \. Dans PowerShell c’est le backtick `. L’antislash est pris littéralement, et la commande est coupée au mauvais endroit.
2. Les guillemets simples. PowerShell ne les traite pas comme bash. Le JSON s’est fait découper, et curl a pris application pour un nom d’hôte.

La seconde erreur est une conséquence de la première : le corps de la requête n’ayant jamais été envoyé, request.body valait undefined.

La commande qui marche, sur une seule ligne

curl.exe -X POST localhost:3000/tasks -H "Content-Type: application/json" -d "{\"title\":\"Maquette\",\"projectId\":\"fantome\"}"

Trois différences : curl.exe (le vrai curl livré avec Windows 10+), guillemets doubles partout, et \" pour échapper les guillemets du JSON.

Leçon générale : quand un test échoue avec une erreur qui semble absurde, soupçonner d’abord la commande de test avant de suspecter le code. Une grande partie des « bugs » de ce projet étaient en fait des commandes mal tapées.

Les relations entre les tables

Un champ texte est une convention. Une relation est une contrainte que la base fait respecter.

Le problème : la tâche orpheline

vérifié par test

Pourquoi : avant les relations, projectId était un simple String. Rien dans la base ne le reliait à la table Project.

Test effectué : créer une tâche avec "projectId":"projet-qui-nexiste-pas".
Résultat : HTTP 201 — la tâche est créée, et vérifié ensuite en base : elle est bien là, pointant vers un projet fantôme.

Le type TypeScript croyait que projectId désignait un projet. La base, elle, stockait du texte. C'est le même problème que l'enum : le type dit une chose, la base ne l'impose pas.

Une relation, c'est deux champs

validé
model User {
  id           String    @id @default(uuid())
  name         String
  email        String    @unique
  passwordHash String
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
  projects     Project[]        // le bras « plusieurs »
}

model Project {
  id        String   @id @default(uuid())
  name      String
  ownerId   String               // le scalaire : la colonne réelle
  owner     User     @relation(fields: [ownerId], references: [id])
  //                                 ↑ le champ de relation : le lien virtuel
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  tasks     Task[]
}
  • Le scalaire (ownerId String) est la donnée stockée en base.
  • Le champ de relation (owner User) n'est pas une colonne : c'est un lien virtuel que Prisma matérialise quand on le demande.
  • @relation est le pont : fields: [ownerId] = « la colonne est chez moi », references: [id] = « elle pointe vers id chez l'autre ».
  • L'autre côté est un tableau (Project[]), parce qu'un utilisateur a plusieurs projets. Les deux côtés doivent être déclarés.
Pourquoi ownerId existait déjà : fields: [ownerId] ne crée pas la colonne, il la désigne. Si elle n'existait pas, Prisma annoncerait « champ inconnu ». Déclarer ownerId String dès le début n'était donc pas provisoire : c'était la moitié scalaire de la relation.

Que devient le parent quand on le supprime ?

vérifié par test

Pourquoi : c'est la question à se poser avant de supprimer une ligne qui a des enfants.

-- SQL généré par Prisma
CONSTRAINT "Task_projectId_fkey" FOREIGN KEY ("projectId")
  REFERENCES "Project" ("id") ON DELETE RESTRICT ON UPDATE CASCADE
RESTRICT (le défaut)La suppression est bloquée si des enfants existent. Échoue bruyamment.
CASCADELes enfants sont supprimés aussi. Silencieux.
Test effectué : un projet avec 2 tâches, on tente de le supprimer.
Résultat : REFUSEE, code P2003 — et les 2 tâches sont intactes.
La base ne supprime PAS les tâches. Elle refuse la suppression.
Pour TaskFlow, RESTRICT est le bon choix. Supprimer un projet ne doit jamais emporter les tâches de quelqu'un. Le jour où on voudra le supprimer, il faudra d'abord décider du sort de ses tâches — et c'est exactement la décision qu'on veut forcer. Pour obtenir CASCADE, il faut l'écrire : @relation(..., onDelete: Cascade).
Question de rappel

Tu supprimes un projet qui a 3 tâches. Que fait la base avec le comportement par défaut, et quel code d'erreur Prisma renvoie-t-il ?

La migration ne répare pas les données invalides

contre-intuitif

Pourquoi : on pourrait croire qu'ajouter une relation échouera s'il existe déjà des orphelines. C'est faux.

-- SQL généré pour ajouter la relation
PRAGMA defer_foreign_keys=ON;
PRAGMA foreign_keys=OFF;          -- la contrainte est DÉSACTIVÉE
CREATE TABLE "new_Task" (... CONSTRAINT "Task_projectId_fkey" ...);
INSERT INTO "new_Task" (...) SELECT ... FROM "Task";   -- copie SANS vérifier
DROP TABLE "Task";
ALTER TABLE "new_Task" RENAME TO "Task";
PRAGMA foreign_keys=ON;
Pourquoi : SQLite ne peut pas modifier une table en place. Prisma la recrée entièrement — et pendant cette reconstruction, les clés étrangères sont coupées, donc les orphelines sont copiées sans contrôle.
Mesuré : après la migration, l'orpheline était toujours en base, mais une nouvelle orpheline était refusée. La contrainte existe (PRAGMA foreign_keys = 1) et s'applique aux écritures suivantes.

Leçon : déclarer une relation ne répare pas les données déjà invalides. Elle empêche seulement d'en créer de nouvelles. Une base héritée avec des orphelines doit être nettoyée à la main.

Les codes d'erreur Prisma à connaître

validé
P2025Enregistrement requis introuvable. Arrive sur update et delete quand la ligne n'existe pas. → HTTP 404
P2003Contrainte de clé étrangère violée. Arrive sur create quand le parent n'existe pas. → HTTP 400
La règle absolue du catch : toujours terminer par throw error;. Sans lui, tu transformes n'importe quel bug inconnu (faute de frappe dans un nom de champ, base injoignable…) en erreur muette, et tu passes des heures à chercher.
Pourquoi tester instanceof avant de lire .code : toutes les erreurs n'ont pas de .code. Sur une TypeError, lire .code renvoie undefined — pas un plantage, donc le test passe « à travers » silencieusement.
} catch (error) {
  if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === "P2003") {
    response.status(400).json({ error: "contrainte de clé étrangère" });
    return;
  }
  throw error;   // ← obligatoire
}

Choisir les champs renvoyés

include prend tout. select prend ce que tu listes.

Le danger d'include

vérifié par test

Pourquoi : include renvoie la relation entière. Avec un include imbriqué, on a obtenu ceci :

{
  "project": {
    "owner": {
      "id": "dda8e6e5-...",
      "name": "Alice",
      "email": "alice@x.com",
      "passwordHash": "$2b$10$HASHSUPERSECRET"   ← ← ←
    }
  }
}
Pas de faille sophistiquée : une seule ligne de code bien innocente, écrite pour « renvoyer les infos utiles ». Le hash ne permet pas de retrouver le mot de passe directement, mais il permet de l'attaquer hors ligne — l'attaquant le récupère une fois, puis teste des millions de candidats chez lui, à sa vitesse, sans que le serveur le voie.

select : la liste blanche

validé
const task = await prisma.task.findUnique({
  where: { id: request.params.id },
  select: {
    id: true,
    title: true,
    status: true,
    project: {
      select: {
        id: true,
        name: true,      // ownerId exclu
      },
    },
  },
});
  • select remplace tout l'objet d'options. On n'écrit plus include.
  • Chaque champ voulu s'écrit true. Ce qui n'est pas listé n'arrive pas.
  • Pour une relation, on imbrique un select dans le select. Écrire project: true à l'intérieur d'un select reprendrait toute la relation, ownerId compris.
Deux bénéfices d'un coup : la sécurité — on ne peut pas fuiter un champ qu'on n'a pas listé, car le défaut est « rien » et non « tout » ; et la performance — la base ne transporte que les colonnes servies.
Le réflexe : avant d'écrire include, se demander « de quoi le client a-t-il besoin ? » et le lister. Ne jamais renvoyer un objet base de données brut.
Question de rappel

Dans un select, tu écris project: true. Qu'arrive-t-il, et pourquoi faut-il imbriquer un second select ?

Une API est un contrat

à corriger

Pourquoi : aujourd'hui, GET renvoie {"data": ...} alors que POST et DELETE renvoient la tâche directement. Trois routes, deux formats.

Conséquence : le client qui consomme l'API ne lit pas le code source, il lit la documentation. Il doit écrire const task = response.data ?? response; — c'est-à-dire deviner la forme. Chaque consommateur devine différemment, et le jour où un format change sans le vouloir, ça casse chez eux sans que rien ne casse chez soi.

La règle : une seule forme de réponse pour toute l'API. On uniformisera tout en {"data": ...}, et on généralisera le {"error": "..."} avec une gestion d'erreurs typée.
