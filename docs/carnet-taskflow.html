Repères du projet

TaskFlow est une API de gestion de projets et de tâches. Le code de travail est dans le dépôt GitHub public de l’apprenant.

À retenir : le navigateur fait une requête HTTP ; Node exécute le serveur ; Express associe une requête à une route ; TypeScript vérifie les types avant l’exécution.
Node.js24.18.0 sur la machine de l’apprenant ; ligne 24 LTS.
pnpm12.6.0, version épinglée dans le projet.
TypeScript7.0.2, compilateur installé en dépendance de développement.
Express5.2.1 avec les types Express 5.0.6.

Les versions et conventions doivent être revérifiées avant d’ajouter un nouvel outil ou une nouvelle commande.

01

Semaine 1 · fondations TypeScript

Un type décrit les formes autorisées ; il ne crée pas à lui seul de données à l’exécution.

1. Alias d’objet : décrire un utilisateur

validé

Pourquoi : TypeScript peut vérifier qu’un objet contient les propriétés attendues. type User décrit la forme ; currentUser contient une valeur réelle.

type User = {
  id: string;
  name: string;
  email: string;
};

const currentUser: User = {
  id: "user-001",
  name: "Elfred",
  email: "elfred434@gmail.com",
};
Ponctuation : dans la définition du type, les propriétés sont séparées par des points-virgules ; dans l’objet de valeurs, elles sont séparées par des virgules. Les textes ont des guillemets.
Question de rappel

Si email vaut le nombre 42, le contrôle TypeScript doit signaler une incompatibilité : email attend un string.

2. Interface : décrire un projet

validé

Pourquoi : une interface décrit elle aussi une forme d’objet. Ici, Project est le contrat des données d’un projet ; currentProject est l’objet qui le respecte.

interface Project {
  id: string;
  name: string;
  ownerId: string;
}

const currentProject: Project = {
  id: "proj-001",
  name: "Apprendre Tanstack",
  ownerId: "user-001",
};
À retenir

Pour ces formes d’objet simples, un alias type et une interface peuvent tous deux convenir. Il n’y a pas une règle absolue qui rendrait l’un toujours supérieur à l’autre.

3. Union : limiter les statuts

validé

Pourquoi : un string libre autoriserait les fautes de frappe. Une union de chaînes littérales limite la valeur à des choix connus ; | signifie « ou ».

type TaskStatus = "todo" | "in-progress" | "done";

type Task = {
  id: string;
  title: string;
  projectId: string;
  status: TaskStatus;
};

Une valeur "finished" n’est pas membre de cette union, donc le contrôle TypeScript la refuse dans le code typé.

Limite importante : le type ne valide pas automatiquement un JSON reçu sur HTTP. Les données externes devront être contrôlées à l’exécution avec Zod plus tard.

4. Générique : réutiliser une enveloppe

validé

Pourquoi : le paramètre T est un emplacement réservé à un type. Le type choisi au moment de l’utilisation précise ce que contient data.

type ApiResponse<T> = {
  data: T;
};

// T devient Task
const oneTask: ApiResponse<Task> = {
  data: currentTask,
};

// T devient un tableau de Task
const manyTasks: ApiResponse<Task[]> = {
  data: tasks,
};
Question de rappel

Dans ApiResponse<Project>, T est remplacé par Project ; data doit donc avoir la forme d’un projet.

5. Tableau : représenter une liste

validé

Pourquoi : l’API doit pouvoir représenter plusieurs tâches. Task[] désigne un tableau dont chaque élément doit respecter Task.

export const tasks: Task[] = [currentTask];

export const tasksResponse: ApiResponse<Task[]> = {
  data: tasks,
};

Le tableau contient une tâche pour l’instant ; on pourra en ajouter d’autres quand on construira les opérations d’écriture.

6. Vérifier n’est pas exécuter

validé

pnpm exec tsc --noEmit vérifie le projet sans générer de JavaScript. pnpm exec tsc compile selon tsconfig.json ; node dist/server.js exécute ensuite le JavaScript généré.

pnpm exec tsc --noEmit  # contrôle seulement
pnpm exec tsc           # génère dist/
node dist/server.js     # lance le serveur

7. Importer une valeur d’un autre fichier

validé

export rend une valeur disponible hors du fichier ; import la réutilise. Avec ESM et NodeNext, l’import relatif indique l’extension JavaScript qui sera émise, même si le fichier source est .ts.

// src/server.ts

8. Une route associe méthode et chemin

validé

Une route Express choisit un gestionnaire selon la méthode HTTP et le chemin. Dans http://localhost:3000/tasks/current, le chemin est /tasks/current ; le navigateur utilise GET.

app.get("/tasks/current", (_request, response) => {
  response.json(currentTaskResponse);
});

app.get("/tasks", (_request, response) => {
  response.json(tasksResponse);
});

app.get("/projects/current", (_request, response) => {
  response.json(currentProjectResponse);
});

La même enveloppe générique ApiResponse<T> peut contenir une tâche ou un projet. currentProjectResponse est exporté depuis domain.ts, puis importé par le serveur.

Réponse observée : {"data":{"id":"proj-001","name":"Apprendre TypeScript","ownerId":"user-001"}}

Question de rappel

Pour GET /tasks, la méthode est GET et le chemin est /tasks. Le chemin n’inclut ni le protocole, ni l’hôte, ni le port.

03

Middleware · journaliser les requêtes

Le middleware de journalisation s’exécute avant les routes ; le terminal a déjà affiché GET /tasks.

Une étape avant la route

testé localement

Un middleware peut inspecter une requête et laisser Express continuer. Il est placé avant les routes ; next() transmet le contrôle à la prochaine étape au lieu de terminer la réponse.

app.use((request, _response, next) => {
  console.log(request.method, request.path);
  next();
});

Guide Express sur les middlewares · API Express : req.method et req.path

Question de rappel

Que se passerait-il si ce middleware n’envoyait aucune réponse et n’appelait jamais next() ? La requête resterait en attente.

04

Corps JSON d’une requête

Préparer Express à lire les données JSON envoyées à TaskFlow.

Transformer le JSON reçu en objet JavaScript

validé avec POST

Pourquoi : pour créer une tâche, le client devra envoyer ses informations au serveur. Ces données voyagent dans le corps de la requête HTTP. Le middleware intégré express.json() lit les requêtes déclarées comme JSON et place le résultat analysé dans request.body.

Le trajet : texte JSON envoyé par le client → express.json() → objet JavaScript disponible dans request.body → route Express.
// Après const app = express(), avant les routes
app.use(express.json());
Deux actions différentes : express.json() fabrique la fonction middleware ; à elle seule, elle ne l’ajoute pas à l’application. app.use(...) l’enregistre pour qu’Express l’exécute. Dans app.use(express.json()), l’appel intérieur se fait d’abord, puis sa fonction résultat est donnée à app.use. Écrire seulement express.json(); crée la fonction puis l’ignore. C’est une syntaxe valide, donc TypeScript ne peut pas deviner l’intention manquante.

Place app.use(express.json()) après la création de app et avant les routes qui lisent request.body. Le middleware ne vérifie pas que les champs reçus sont corrects : les données envoyées par un client restent à valider.

Documentation officielle Express 5 : express.json()

Question de rappel : que fait chaque partie ?

express.json() crée le middleware ; app.use(...) l’enregistre. Ensemble, ils font analyser le corps JSON et rendent le résultat accessible sur request.body. Cela ne garantit pas que title est présent ou que status est autorisé : cette validation viendra plus tard.

05

POST /tasks · demander la création d’une tâche

On distingue lire la liste et demander l’ajout d’une tâche.

La méthode HTTP et le chemin choisissent la route

testé

Pourquoi : GET /tasks sert à lire la liste existante. Pour demander au serveur de créer une tâche, TaskFlow utilisera POST /tasks et les données du corps JSON. Le chemin reste /tasks, mais la méthode change ; Express distingue les deux routes par cette paire méthode + chemin.

À comparer :
GET /tasks → lire la liste
POST /tasks → demander la création d’une tâche à partir des données envoyées

Important : le mot POST ne sauvegarde rien à lui seul. Il sélectionne un gestionnaire. C’est le code de ce gestionnaire qui devra lire request.body et ajouter la tâche au tableau en mémoire.

Dans le gestionnaire, trois actions

  1. Importer le tableau tasks depuis domain.ts : c’est la liste gardée en mémoire.
  2. Appeler tasks.push(request.body) : push ajoute l’objet reçu à la fin du tableau. request.body vient du middleware JSON.
  3. Renvoyer tasksResponse avec response.json(...) ; son enveloppe data contient ce même tableau mis à jour.
app.post("/tasks", (request, response) => {
  tasks.push(request.body);
  response.json(tasksResponse);
});
Garder la même forme de réponse : tasks est le tableau brut ; tasksResponse est l’objet enveloppe { data: tasks }. Utiliser response.json(tasksResponse) dans POST conserve la même forme que GET. Dans le gestionnaire Express, request est déjà fourni comme paramètre : aucun import { request } from "http" n’est nécessaire.
Limite de cette première version : request.body vient d’un client et n’est pas validé automatiquement par TypeScript. Pour l’exercice, envoie un objet qui respecte bien la forme Task. Plus tard, Zod vérifiera les données reçues. Le tableau est en mémoire : le redémarrage du serveur le réinitialise.

Pour notre premier test, le corps sera un objet de forme Task avec id, title, projectId et status. Nous fournirons l’id manuellement pour l’exercice ; sa création automatique viendra plus tard.

Pour tester la route, PowerShell doit envoyer un corps JSON. Si un accent ressort sous la forme � jusque dans la réponse vue au navigateur, il a été remplacé avant d’être stocké : ce n’est pas seulement l’affichage du terminal. Selon la version de PowerShell, envoyer directement une chaîne peut mal encoder les caractères Unicode. On peut convertir explicitement le texte en octets UTF-8 et déclarer cet encodage :

$taskJson = '{"id":"task-003","title":"Créer via POST","projectId":"proj-001","status":"todo"}'
$utf8Body = [System.Text.Encoding]::UTF8.GetBytes($taskJson)
Invoke-RestMethod -Uri "http://localhost:3000/tasks" `
  -Method Post `
  -ContentType "application/json; charset=utf-8" `
  -Body $utf8Body

GetBytes transforme la chaîne en octets UTF-8 ; charset=utf-8 indique à Express comment les décoder. Si l’accent est déjà remplacé quand tu affiches $taskJson avant l’envoi, le problème se situe plus tôt.

Documentation Microsoft : Invoke-RestMethod · Exemple du problème Unicode dans Invoke-RestMethod

Question de rappel : pourquoi GET et POST peuvent-ils partager /tasks ?

Parce que la méthode HTTP fait partie de l’identification de la route, avec le chemin.

Question de rappel : que fait tasks.push(request.body) ?

push ajoute l’objet reçu à la fin du tableau en mémoire. Cela ne valide pas l’objet et ne l’écrit pas sur le disque.

Un paramètre d’URL pour viser une tâche

Passer l’identifiant d’une tâche dans le chemin de la requête.

Le placeholder :id

notion en cours

Pourquoi : GET /tasks vise toute la liste. Pour viser une tâche particulière dans TaskFlow, le chemin peut contenir son identifiant. Le symbole : indique à Express qu’un morceau du chemin doit être capturé comme paramètre.

Exemple TaskFlow :
Modèle de route : /tasks/:id
Requête reçue : /tasks/task-003
Valeur capturée : request.params.id vaut la chaîne "task-003"

:id est le nom donné au paramètre dans le modèle de route. request.params.id est la valeur réelle capturée dans l’URL ; ici, c’est un texte, car les identifiants Task sont des chaînes.

07

Retrouver une tâche dans le tableau

Utiliser l’identifiant capturé dans l’URL pour repérer l’objet correspondant.

La méthode find()

testé

Pourquoi : request.params.id donne l’identifiant demandé, mais ce texte n’est pas la tâche elle-même. tasks.find(...) parcourt le tableau et cherche le premier élément qui satisfait une comparaison.

const foundTask = tasks.find(
  (oneTask) => oneTask.id === request.params.id
);
  • oneTask représente l’élément examiné à chaque tour.
  • === vérifie si son identifiant est exactement égal à celui capturé dans l’URL.
  • find() renvoie l’objet trouvé, ou undefined si aucun élément ne correspond.
Application TaskFlow : avec GET /tasks/task-002, la route reçoit request.params.id === "task-002", puis recherche la tâche dont id vaut "task-002".
Test observé : GET /tasks/task-001 et GET /tasks/task-002 ont chacun renvoyé l’objet correspondant sous data.

La route GET /tasks/:id est placée après la route statique GET /tasks/current : ainsi, :id ne capture pas le mot current. La réponse « identifiant absent » sera traitée dans l’étape suivante ; ici, on teste d’abord un identifiant qui existe.

Question de rappel

Si la liste contient une tâche avec id: "task-002", quel objet find() renvoie-t-il quand l’URL est /tasks/task-002 ?

08

Répondre si l’identifiant est introuvable

Une recherche peut réussir ou ne trouver aucun objet.

Le résultat absent et le statut 404

testé

Pourquoi : find() renvoie undefined si aucun identifiant ne correspond. L’API ne doit pas faire croire qu’une tâche existe : elle doit répondre 404 Not Found, c’est-à-dire « ressource introuvable ».

app.get("/tasks/:id", (request, response) => {
  const foundTask = tasks.find(
    (oneTask) => oneTask.id === request.params.id
  );

  if (!foundTask) {
    response.status(404).json({ error: "Tâche introuvable" });
    return;
  }

  response.json({ data: foundTask });
});
  • if (!foundTask) vérifie qu’aucune tâche n’a été trouvée. Ici, !undefined vaut true.
  • response.status(404) choisit le code HTTP ; .json(...) envoie aussi un message JSON.
  • return arrête le gestionnaire après la réponse d’erreur ; sinon le code pourrait continuer et tenter d’envoyer une deuxième réponse.
Pourquoi return est indispensable : le bloc if ne met pas fin à toute la fonction. Sans return, après avoir envoyé le JSON 404, JavaScript sort seulement des accolades du if puis continue à la ligne suivante, qui essaie d’envoyer aussi la réponse normale. Node refuse cette deuxième réponse et affiche ERR_HTTP_HEADERS_SENT. Le return fait quitter immédiatement le gestionnaire après le 404.
Résultat attendu : GET /tasks/id-inexistant reçoit le statut 404 et le JSON {"error":"Tâche introuvable"}. Pour une tâche existante, la réponse reste {"data":{...}}.
Question de rappel

Pourquoi met-on return après l’envoi de la réponse 404 ? Pour sortir du gestionnaire et ne pas tenter ensuite d’envoyer aussi la réponse normale.
